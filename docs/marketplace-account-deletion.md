# Marketplace Account Deletion callback

Verified against the [eBay Marketplace User Account Deletion guide](https://developer.ebay.com/develop/guides/sell/marketplace-user-account-deletion), [eBay's Node event notification SDK](https://github.com/eBay/event-notification-nodejs-sdk) (`lib/validator.js`, `lib/client.js`), and [Notification API release notes](https://developer.ebay.com/api-docs/commerce/notification/static/release-notes.html) on 2026-10-11. No account-specific eBay notification has been received or verified yet. The SDK uses Node crypto and an Express example, so the Worker implements its documented wire behavior with WebCrypto rather than bundling the Node package. The real eBay test notification remains a review checkpoint.

## Endpoint and configuration

The public callback is `GET` and `POST https://<your-worker-host>/ebay/account-deletion`. Set `EBAY_ENVIRONMENT` explicitly to `sandbox` or `production`. Set `EBAY_DELETION_ENDPOINT` to the **exact** HTTPS URL that will be entered in eBay's portal, without a query string or trailing slash. Set `EBAY_DELETION_VERIFICATION_TOKEN` as a Worker secret: 32–80 letters, digits, underscores or hyphens, generated randomly. Set an independent, stable 32-byte base64 `EBAY_DELETION_HASH_KEY` as a Worker secret. The existing `EBAY_CLIENT_ID` and `EBAY_CLIENT_SECRET` are needed for an application token used to read eBay's public signing key. Keep all real values out of this public repository and coding-agent shell access.

The GET handler returns `SHA-256(challenge_code + verification token + exact endpoint URL)` as lowercase hexadecimal JSON `challengeResponse`. POST requires `application/json`, a bounded body, and a valid `x-ebay-signature`. The header is base64 JSON containing `kid` and a DER ECDSA signature. The Worker obtains the key with an application token from the selected eBay environment, caches it for at most an hour, and verifies SHA-1 ECDSA over `JSON.stringify(parsedMessage)` to match eBay's Node SDK. Invalid signatures return 412; unavailable key retrieval, configuration or D1 returns 503. Neither path logs payloads, identifiers, signatures or tokens.

Successful POST returns 204 only after the D1 transaction commits. eBay accepts 204 and retries unacknowledged messages. The transaction inserts a keyed notification hash into `ebay_deletion_inbox`, deletes mapped local rows, then removes their subject links. Replayed notification IDs with the same immutable `userId` are acknowledged without repeating work. A conflicting notification ID is rejected. The inbox contains keyed hashes and processing time, never raw notification JSON or eBay identifiers. **Do not rotate the hash key without a planned reindex of all subject links**; losing it makes existing links unmatchable.

## Data coverage and registration gate

`004_ebay_account_deletion.sql` creates `ebay_subject_links`. An eBay data ingestion path must register each eBay `userId`, `username` and `eiasToken` association using `subjectHash` before it can store data about that person. A `sale_item` link targets `sale_items.id`; deletion removes its `listing_drafts` first, then the sale item and all aliases. A `seller_connection` link targets its environment (`sandbox` or `production`); deletion removes the encrypted OAuth token row. These are the only covered target types. Missing links mean no match, not proof that no personal data exists.

Current v1 sale items and drafts are synthetic local data. No buyer, order, message, image, label or other real eBay person data store exists in this checkout. The current seller OAuth connection does **not** record a seller `userId`, so it cannot yet be linked to an account deletion subject. The receiver refuses to acknowledge **any** notification while a seller connection exists without an immutable `userId` link. Before production registration, review actual D1 contents and every data path, establish seller identity linkage when real seller authorization is enabled, backfill any existing records, and extend deletion coverage for every new person-data store. Do not persist real eBay person data in arbitrary `sale_items.facts_json`, draft text, logs or fixtures without a complete index and deletion plan. Unknown notification schema versions or missing immutable `userId` are rejected and not acknowledged.

The transaction removes active D1 rows, but [D1 Time Travel can restore earlier database states](https://developers.cloudflare.com/d1/reference/time-travel/) within its retention window. Any separate exports or backups also need a deletion procedure. Before production use, document backup retention, prohibit restoration without replaying the deletion inbox, and complete a legal/privacy review of irreversible deletion and any required retention exceptions. This receiver does not claim to erase provider backups immediately.

## Review steps before eBay registration

1. Review the schema inventory, subject-link coverage, D1 backup/export policy, and the real endpoint's Cloudflare routing. The callback must be publicly reachable while `/mcp` keeps its existing authorization. Keep Cloudflare Access and deployment values outside this repo.
2. Apply migration 004 to the intended isolated database and configure secrets through the deployment's private secret manager. Use the same exact endpoint and verification token in the eBay portal. Do not use the example values.
3. After approval, deploy to an isolated environment, test the GET challenge and eBay's Send Test Notification, and verify a signed synthetic account-deletion event removes mapped records and leaves only keyed inbox hashes. Record key ID, signature result, D1 transaction result and eBay delivery status without person identifiers.
4. Register the endpoint only after the account-specific probe and data/backup coverage review pass. Registration and production deployment are outside this change.
